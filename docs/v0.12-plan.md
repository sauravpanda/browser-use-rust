# v0.12.0 Plan — Structural Rewrite for Cost Reduction

**Status:** v0.12.x patch series in progress; v0.12.17 lands the Option-2 structural rewrite (render mode), awaiting dashboard eval.
**Last updated:** 2026-08-13

## Current 0.12.x Patch Plan

The 0.12.8-0.12.10 work lowered cost incrementally, but the main remaining
gap versus Python is still per-step prompt size: Rust is around 12.4k prompt
tokens/step while Python is around 5.6k prompt tokens/step.

### v0.12.11 result

Run `kh7eqafkbmkmh55nj3hmps86t5874gpy` made the agent cheaper by ending
blocked/search-loop tasks earlier, but the success tradeoff was too large:

- Success fell from 149/198 in 0.12.10 to 133/198 in 0.12.11 (-8.08pp).
- Avg cost fell from `$0.054125` to `$0.047429` (-12.37%).
- P90 steps fell from 34 to 26.
- Give Up failures rose from 35 to 51.
- Prompt tokens per step stayed flat at about 12.4k, so the cost win came from
  shorter runs, not from cheaper turns.

### v0.12.12 adjustment

Ship a narrow correction before continuing the deeper prompt cleanup:

- Keep the shared blocked-site policy and anti-loop nudges from 0.12.11.
- Restore the softer 0.12.10 blocked/search force-final thresholds:
  blocked window 8, force at 5 blocked states after step 15; search fallback
  window 8, force at 6 search states after step 20.
- Allow bounded external-result completion when all target-site variants are
  blocked and a visible result title/snippet/URL directly answers a static
  public fact.
- Continue rejecting snippet-only completion for live/current data, prices,
  availability, bookings, account-gated pages, locators, or actions that must
  be performed on the site.

Expected effect: recover a meaningful share of the 27 pass-to-fail regressions
from 0.12.11 while preserving some of the step/cost tail reduction.

### v0.12.12 result

Run `kh7fwtazjq9bc9d2s40wtbgqsx8740cw` recovered part of the 0.12.11
success regression, but gave back the cost win:

- Success improved from 133/198 in 0.12.11 to 140/198 (+3.54pp), slightly
  above the Python baseline of 138/198.
- Avg cost rose from `$0.047429` to `$0.055607`, slightly worse than 0.12.10
  (`$0.054125`).
- Avg steps rose from 14.40 to 15.38, still lower than 0.12.10's 16.49.
- P90 steps stayed improved at 28 versus 34 in 0.12.10.
- Prompt tokens per step worsened to about 13.1k, so the next slice should
  remove redundant finalization turns rather than add more prompt policy.

Trace detail showed 100/198 tasks called `done` twice and 102/198 had a
provisional finalization turn. Those provisional-final tasks averaged about
`$0.0614` versus `$0.0487` for the rest.

### v0.12.13 adjustment

Disable global self-validation by default while keeping the targeted
final-answer recovery nudges and list-count guard:

- Default `Agent(..., self_validate=False)`.
- Preserve explicit `self_validate=True` for callers that want the old
  confirmation-turn behavior.
- Keep task-specific recovery nudges before finalization.
- Keep `_done_count_check_message` so underspecified top-N/list answers still
  get one correction turn.

Expected effect: remove one LLM round trip from many successful tasks, reducing
steps and completion/prompt cost without touching browsing behavior.

### v0.12.13 result

Run `kh70ap03gg75bhzqvb2zek6ss1876dc8` proved the finalization cost lever,
but the accuracy loss was too large:

- Success fell from 140/198 in 0.12.12 to 132/198 (-4.04pp).
- Avg cost fell from `$0.055607` to `$0.046901` (-15.66%).
- Avg steps fell from 15.38 to 13.63.
- P90 steps fell from 28 to 26.
- Incorrect Result failures rose from 16 to 24.

The change worked mechanically: validation prompt turns went to zero, and
double-`done` tasks fell from 100/198 to 1/198. The removed validation was
catching real bad finals, so fully disabling it is not a good baseline.

### v0.12.14 adjustment

Use selective lightweight validation instead of global-on or global-off:

- Default `Agent(..., self_validate=True, self_validate_risk_only=True)`.
- Validate high-risk finals only: search/filter/sort/locator tasks, counted
  top/first/list tasks, recency/current/latest tasks, price/date/availability
  tasks, and blocked/external-evidence finals.
- Skip validation for low-risk static summaries.
- Shorten the validation prompt to a compact three-point check.
- Preserve `self_validate_risk_only=False` for callers that want the old
  validate-every-final behavior.

Dry-run over the 0.12.13 traces estimates validation would apply to about
73 successful step>=3 tasks, rather than the 102 provisional finalization
turns observed in 0.12.12.

### v0.12.17 — render mode (Option 2, radicalized)

Supersedes the previously planned "guidance dedupe" slot. Structural
review of v0.5.0→v0.12.10 concluded the transcript had been converging
on upstream's re-render design one patch at a time (collapse ≈
agent_history_items, `<memory>` tags ≈ memory carryover, FIRST_N/LAST_M
≈ max_history_items, ephemeral lifecycle ≈ read_state, supersede ≈
wholesale state replacement, STATE_UNCHANGED ≈ cacheable-prefix
ordering) while still paying the transcript's structural taxes:
tool_use/tool_result pairing bookkeeping, pop-order corruption
fallbacks, and — decisive — mid-list mutation every step, which is
re-render semantics billed at cache-write prices (the CACHE READ DROP
detector exists because of exactly this). Wire format and context
construction are separate axes: native tool calling stays (that's the
output-token win); context construction moves to per-step re-render.

Shipped:

- **`context_mode="render"` (new default).** The LLM input is rebuilt
  every step: task message(s) → `[AGENT_HISTORY]` machine-derived
  journal (rendered fresh from the `HistoryItem` journal, FIRST_N=3 /
  LAST_M=12 windowing) → at most ONE recent native tool turn
  (`render_keep_native_turns`, default 1; 0 = pure re-render with a
  `[LAST_TURN_RESULTS]` text block) → one fresh page-state message
  with `<agent_state>` (the model's own memory tags), `<read_state>`,
  DOM, and `<step_info>` at the volatile tail. Post-call nudges
  (validation, INDEX_DEAD, count-check, loop nudges) survive exactly
  one rebuild via a seen-watermark — all ~40 injection sites work
  unchanged. `_collapse_old_history`, page-state supersede, and the
  v0.12.10 STATE_UNCHANGED reuse hack are inert in render mode (the
  reuse hack was treating a symptom of transcript mutation).
  Escape hatch: `context_mode="transcript"` or
  BU_RS_CONTEXT_MODE=transcript restores the old path wholesale.
- **`tool_choice` as the enforcement mechanism** (provider-agnostic in
  `llm/base.py`; mapped in anthropic/openai/google, groq/azure
  inherit). Last step and `_force_final_answer` force
  `{"name": "done"}` — upstream's DoneAgentOutput schema swap done
  natively; empty-output and prose-only-action turns force
  `"required"` on the retry. Gated on the provider signature so
  external BaseChatModel impls and test fakes are unaffected.

Expected cost mechanics: stable cached prefix becomes
[system + tools + task + journal-prefix]; per-step uncached cost is
~1.0× (DOM + journal + last turn), flat in step count instead of
linear in surviving history. Predicted from the v0.12 plan's own
observation: "even cached, every step pays cache_read on the entire
prior history."

Gates (same variance rules as v0.12.0):
- Accuracy within ±5pp of 0.12.16 on the dashboard run.
- cost/M tokens — expect a level SHIFT: cache-hit% will drop (less
  cached volume exists at all) while absolute cost/task should fall on
  long tasks. Judge on cost/task median + tail, not cache-hit%.
- No system_prompt_hash / tools_hash drift (both prompts and tool
  schemas are byte-identical to 0.12.16 in this ship).
- Watch task-2226-class regressions (re-fetching content): the
  read_state TTL + spill-to-file channel is now the ONLY carrier for
  old read content beyond one turn. If re-fetch loops appear, first
  lever is EPHEMERAL_RESULT_WINDOW_STEPS, not reverting the mode.

### v0.12.18 — render-mode read retention

First finding from the v0.12.17 new-eval-platform comparison
(WebBench READ v5, gemini-3-flash-preview, laith judge, cloud
browsers): browser-use main 84.3% / 17.1 avg steps / $0.080 vs
browser-use-rs 0.12.17 73.2% / 24.7 avg steps / $0.101. Render mode's
structural cost win is real (cache-hit 67% vs 24%, $/Mtok 0.325 vs
0.645) but is eaten by step inflation.

Root cause of the 11pp gap (34 py-only-pass vs 12 rs-only-pass): the
v0.5.0 read-retention bug, reintroduced. In render mode a tool result
survives exactly one rebuild, and the read_state lifecycle's 25KB
threshold — tuned for transcript mode where small reads stayed native
forever — let every sub-25KB extract/search result fall through both
nets. Trace signature (task 361): the agent extracts the correct
answer, loses it at the next rebuild, re-fetches into a shifted page,
and either grind-loops (13 tasks at 50-100 steps, same call repeated
up to 23×) or finalizes from its lossy <memory> paraphrase
(judge: synthetic-or-unsupported 12, result-final-mismatch 6,
empty-result 7). Failing tasks median 6 read calls vs 2 on passes.

Ship (render mode only; transcript unchanged):
- EPHEMERAL_RESULT_THRESHOLD_RENDER=200 — essentially every read
  result flows through <read_state> (TTL 2) + spill file + stub.
- EPHEMERAL_RESULT_TOOLS_RENDER adds extract_result_cards,
  search_page, find_elements, find_text (the tools whose discarded
  results drove the loops); alias-canonicalized at dispatch.
- Journal lines for read tools widened 120 → 500 chars.
- No prompt or tool-schema change: the FLASH prompt's
  read_state_lifecycle section already documents this exact contract,
  so system_prompt_hash and tools_hash stay stable.

Gate: re-run the WebBench gemini cell; expect avg steps to drop
toward the py baseline's 17 and the synthetic/empty failure classes
to shrink. Judge on cost/task median + accuracy vs the 0.12.17 cell.

### v0.12.19 attempt — safe batching — REJECTED

Lever from the bakeoff step decomposition: on both-pass WebBench tasks
rs spent 15.1 turns to py's 11.8 for near-identical action counts
(14.8 vs 14.0), with ~2.7 turns attributed to batching (rs 0.98
actions/step vs py 1.19). Ship: retired the v0.4.17
indexed-after-mutation batch guard (keeping only the URL-change abort,
upstream semantics) and rewrote both prompts to encourage 2-3 action
batches, relying on selector retargeting to absorb stale indices.

Result (run 32301133812 vs the 0.12.18 cell):

- Mechanism moved as designed: actions/step 1.00 → 1.17, multi-action
  turns 0.4 → 3.7/task, task 1898 (the traced guard victim) flipped to
  pass with zero guard skips.
- Outcome did not: steps flat (22.2 → 22.0), time +7% (124 → 133s),
  cost +3% ($0.0877 → $0.0903), accuracy 76.8% → 75.3% (noise).
- Why: total actions per task ROSE ~16% (22.2 → 25.7). Stale-index
  retarget recoveries went 116 → 322 (2.8×) and nav-skips 49 → 98 —
  the second action in a same-page batch frequently addresses a DOM
  the first action just moved, so batches buy turns and immediately
  spend them on retargeting round-trips and redone work.
- Reframe: the old guard's premise was right (same-page indices go
  stale after nearly every mutation in bu-dom's walk-order indexing);
  only its remedy was blunt. Upstream affords 1.19 actions/step
  because its element addressing survives same-page mutations more
  often — this lever is actually a bu-dom index-stability question,
  not agent policy. Do not retry prompt-side batching until bu-dom
  gives indices that survive same-page mutation.

### v0.12.21 — interaction coverage (bu-dom + input paths)

bu-bench decomposition located the largest rs↔py gap in one category:
InteractionTests (py 100% vs rs 60% pooled) — browser-use's own
stress-test challenge pages. Local probing against those exact URLs
found five concrete capability gaps, each fixed and re-verified with
the probe (scratchpad probe_challenges.py):

- **Sub-frame viewport culling** (script.js): content below the fold
  of a same-origin iframe was dropped, but page scroll never reveals
  it — iframe-inception indexed 4 of 13 fields. Viewport culling now
  applies to the top document only; actions scrollIntoView at dispatch
  time. 4/13 → 13/13.
- **Occlusion culling killed floating-label form kits** (script.js):
  MUI's notched-outline fieldset covers the input's center, so
  elementFromPoint culled 5 of 7 MUI fields. Native form fields are
  now exempt from the occlusion check (display/opacity/size checks
  still apply).
- **Bare form fields dropped** (script.js): unnamed inputs and empty
  contenteditable editors had no text and no kept attrs and fell to
  the emptiness cull; rich-text forms had ZERO indexed text targets.
  Form fields are exempt; contenteditable roots get a
  contenteditable=true attr (root only — descendants all report
  isContentEditable and would spam one index per paragraph).
- **Date-family inputs unfillable** (bu-browser): Chrome routes
  Input.insertText into the segmented date editor, which drops free
  text — "the date field remained unfilled" in the judged runs.
  type_index now detects date/time/month/week/datetime-local and sets
  the value via the native property setter + input/change events
  (React-compatible).
- **Indexed shadow-DOM elements were unclickable** (bu-browser):
  action-time element resolution used querySelector, which cannot see
  shadow content the snapshot walker indexes. Shared findByIdx helper
  now traverses same-origin iframes AND open shadow roots for
  click/type/scroll_to/upload.

Hidden native inputs with styled replacements (opacity-0 MUI
autocomplete inputs) are intentionally left unindexed — their styled
wrappers are indexed, and click-wrapper → focus-native → insertText
works end to end.

Round 3 (from smoke-8 trajectories):

- **Python tool lookups were top-document-only**: select_dropdown /
  get_dropdown_options / in-container scroll / type_text-clear resolved
  via querySelector and returned "no element with index" for framed and
  shadow elements the snapshot indexes (the iframe challenge burned 10+
  turns retrying a visible select). All share the frame/shadow-aware
  FIND_BY_IDX_JS prelude now.
- **Proxy labels indexed**: a <label> whose bound control is invisible
  (display:none/opacity-0/zero-size styled radios and checkboxes) is
  indexed as the control's only clickable proxy.
- **page_text composes across iframes and shadow roots**: body.innerText
  is blind to both, so the agent filled and submitted correctly but
  could never SEE validation messages or success states (~250 chars of
  chrome on the shadow page). This was the failure texture on several
  judged tasks: correct work, honest "could not verify", judge fail.

Smoke progression on the 4 previously-failing challenge tasks:
0.12.18 0/4 → round 1-2 1/4 → round 3 3/4 (remaining: shadow-dom task
where the agent verified via evaluate_js instead of page_text —
agent-behavior tail, not a mechanical gap).

### v0.12.22 — bounded finalization

Last clean agent-policy lever from the step decomposition: text-only
guard turns cost ~0.6 turns/task (validation intercepts, count-checks)
and are occasionally answer-degrading — task 1898's count-check bounced
a CORRECT done() into 3 stale-index browse steps and a wrong revision.

Ship: after a validation or count-check bounce, force
tool_choice={"name":"done"} on the next call — the re-check may revise
and re-commit but not wander into new browsing. Recovery nudges are
NOT bounded (they direct the agent to a specific page on purpose).
Validation triggers and prompts unchanged (v0.12.13 proved removing
validation outright costs accuracy; this keeps the check and caps its
price at exactly one turn).

Gate vs the 0.12.21 WebBench cell (77.8% / 22.3 steps / $0.0921):
accuracy within ±5pp with steps/cost down a notch; watch
result-final-mismatch — if bounding blocks legitimate fix-up browsing,
it shows up there.

### Architecture gap analysis (2026-08-19) — why python wins repeatedly

Across 5 rust WebBench runs vs python: only 3 tasks are deterministic
rust failures (1211, 1800, 2267), 5 near-deterministic, 25 coin-flips —
python's edge is mostly reliability plus a small hard core. Trajectory
forensics on the hard core, same model both sides:

1. **Perception reach**: python indexes the whole document (element
   indices observed up to 38k/55k); rust viewport-culls. TMDB's filter
   panel (1800) and Newegg's deep tabs (1211) are outside rust's
   addressable world.
2. **Interactivity model**: python clicks `li` tab chips; rust's walker
   classes `li` as static text. On 1211 rust FINDS "Review Bytes →
   Performance/Build Quality" via search_page and cannot click any of
   it — deterministic loss.
3. **Action feedback**: python echoes the field's post-type actual
   value ("Typed '2022-01-01' ⚠️ field's actual value '1/1/20…'");
   rust types blind — 1800's dates silently never applied, 5/5 runs.
4. **Strategy freedom**: python wins 2267 with a 7-variant site: search
   ladder + direct URL synthesis + per-item detail visits; rust's
   SEARCH_FALLBACK force-final and the "three recovery moves" policy
   prohibit exactly that behavior (cost-war scar tissue now acting as
   an accuracy cap — likely also implicated in the GAIA/BrowseComp
   max-outs).
5. **Flaky band (25 tasks)**: failures are all finalization-quality
   classes (scope-drift/synthetic/mismatch/empty) — commits from the
   wrong scope with thin evidence, consistent with 1–4 shrinking what
   it can see and try.

### bcode (browsercode) transferables — 0.12.23+ candidates, EV order

From the ../browsercode architecture study (V4 = no snapshot at all;
the model writes JS/CDP ad hoc; whole-document perception by
construction; screenshots auto-attached from the CDP call-result
stream):

1. **Typed-action read-back** (bcode dropdowns recipe + upstream's
   echo): after type_text/fill, read el.value back and put it in the
   tool result; assert selects the same way (select_dropdown already
   does). Tiny diff, kills the 1800 class. Optional stronger variant:
   register Network.responseReceived waiters before consequential
   clicks (SPA success signal).
2. **Interactive reach**: index off-viewport INTERACTIVE elements
   page-wide (static text stays viewport-culled to protect the DOM
   budget); treat cursor-pointer li/[role=tab] chips as interactive.
   Fixes 1211/1800-class. Watch DOM-size cost per the v0.8.21 lessons.
3. **Evidence budget replaces search clamps**: swap the
   SEARCH_FALLBACK force-final + 3-recovery-move policy for bcode's
   rule — "after three tool calls that add no new evidence toward the
   same missing fact, change source/approach or record an explicit
   limitation" — placed in the done TOOL DESCRIPTION (re-read every
   call), not just the prompt. Unlocks legitimate research ladders
   (2267, GAIA/BrowseComp) while still breaking loops.
3b. Completeness contract in the done tool description ("answer must
   contain every requested value or an explicit evidence-backed
   limitation; never silently substitute a different record/variant").
4. **Recipe knowledge inlined into actions, not docs**: bcode deleted
   its 16 interaction recipes because the model never read them —
   inline the mechanics instead (we already did: date fill, composed
   events, iframe coords; remaining: MUI-autocomplete Enter-commit,
   virtualized-list wheel scroll, network-confirm).
5. Longer-term: persistent cross-call `state` + verified submit-path
   (answer built in a file, verified, then submitted by path) for
   long-answer tasks; bounded-episode receipts if we ever add
   delegation.

### v0.12.27 — think-differently experiments (opt-in only; RC untouched)

Oracle analysis over the five same-config render-family runs reframed
the problem: rust failures are substantially stochastic. Union of any
two runs = 87.9–88.9% (vs python single 84.3%); union of all five =
92.9%. Luna high∪xhigh = 84.3% at $0.055 combined — cheaper than
python's single xhigh ($0.066 for 86.4%). Rust's −35% speed / 2.2×
Luna cost advantage is a retry budget nobody was spending.

Two pre-registered experiments, both opt-in (defaults unchanged, so
the 0.12.26-behavior RC carries zero risk):

**(A) Portfolio best-of-2 with verifier — harness-side.**
`options.max_attempts=2` in harnesses/browser-use-rs: attempt 1 runs
normally; a same-model verifier grades the final answer (complete +
concrete + grounded; give-ups flagged); only a flagged answer triggers
a fresh-browser attempt 2; if both fail verification a chooser picks.
Reported cost sums all attempts + verifier calls (honest); steps =
chosen attempt. Gate vs single-run band 75.3–78.8%/$0.088:

## Option 1 — DOM relevance ranking + budget cap

### Hypothesis
Per-step DOM snapshot is 50-65 KB (vs upstream ~30-35 KB). Median step has ~13-16k tokens of uncached input from the snapshot alone. Cutting per-snapshot bytes by ~30% via prioritization + budget cap should drop median cost ~6-10% with no accuracy loss, IF prioritization preserves the elements the agent actually picks.

### Spec

**1. Element scoring in `crates/bu-dom/src/script.js`** — emit a per-element relevance score during the walk. Inputs:
- **In-viewport bonus** (already implicitly preferred via early DOM walk order, but make explicit): +5
- **Region** (closest ancestor `<header>/<nav>/<main>/<aside>/<footer>` or `[role=...]`): main +3, header +2, nav +2, footer −2, aside −1
- **Element type strength**: `<a href>` +3, `<button>` +3, `[role=button]` +2, `<input>` +3, `[onclick]` +1, `[cursor:pointer]` +0
- **Has accessible name**: text/aria-label/title +2, has only icon/svg child (no name) +0
- **Position-in-flow**: top of document +1, deeply nested +0
- **Static text**: leave as-is, do not score (already culled to narrow tag set)

**2. Top-N budget cap in `to_llm_string()`** — emit interactive elements in `score DESC, tree-order ASC` order, cut at element count = 80 (or byte cap = 35,000, whichever fires first). Static text emitted normally as currently. Below-cut elements available via scroll → re-snapshot.

**3. Prompt addendum** — single paragraph noting the snapshot is "ranked by relevance, top-N visible" so the agent doesn't assume it's seeing everything. Include scroll-to-find guidance.

**4. v0.10.4 instrumentation** — add per-call `elements_emitted` count + `elements_culled` count to detect over-aggressive culling.

### Risk profile
- **HIGH on accuracy**: scoring is heuristic; wrong score → wrong elements → wrong actions. v0.11.0 (40k DOM cap), v0.11.6 (text trim), v0.11.8 (paint-order culling on text) all failed via similar mechanisms.
- **Mitigation 1**: ship behind env-var flag (default OFF); enable only via eval config until validated.
- **Mitigation 2**: cap at 80 elements only — most pages have ≤80 visible interactive elements anyway, so cap rarely fires on simple pages.
- **Mitigation 3**: log culled elements for first 10 eval tasks; manually inspect to confirm cut content is genuinely low-relevance.

### Estimated impact (per cross-experiment subagent analysis)
- Cost: −5-10% per task (median attack)
- Accuracy: tail risk — could lose 3-5pp if scoring is bad
- Tokens: −15-25% per snapshot on dense pages

### Effort
3-5 days:
- Day 1: scoring algorithm in script.js + tests on synthetic DOMs
- Day 2: budget cap + tree-order tiebreak + emit
- Day 3: prompt update + env flag + instrumentation
- Day 4-5: eval-validate, tune scoring weights

## Option 2 — HistoryItem + LLM summarization (USER-PREFERRED)

### Hypothesis
Conversation history grows linearly with steps. Even cached, every step pays `cache_read` on the entire prior history. A 20-step task accumulates ~50-100k tokens of message history. Replacing accumulated raw `(AssistantMessage, ToolResultMessage*)` pairs with a compacted LLM-summarized "memory" string would:
- Cut steady-state cached prefix bytes ~50-70%
- Cut cache_creation cost on the step where summarization fires
- Preserve agent context via structured memory + recent-step retention

This is the architecture upstream Python `browser_use` uses (see `browser_use/agent/message_manager/service.py` and `views.py::HistoryItem`).

### Spec

**1. New `HistoryItem` struct** in `python/browser_use_rs/agent/__init__.py` (or new `_history.py`):
```python
@dataclass
class HistoryItem:
    step: int
    evaluation: str            # from <evaluation_previous_goal>
    memory: str                # from <memory>
    next_goal: str             # from <next_goal>
    actions: list[ActionRecord] # tool calls + their long_term_memory
    error: str | None          # if step had errors
```

Each step produces ONE HistoryItem (not the current 1 AssistantMessage + N ToolResultMessage pairs in self._messages).

**2. ActionRecord** — replaces full ToolResultMessage content with:
```python
@dataclass
class ActionRecord:
    tool_name: str
    args_summary: str       # short repr of args (e.g., "click([5])")
    long_term_memory: str   # 1-line summary suitable for history context
    extracted_content: str | None  # full content, only kept if include_in_memory=True
```

**3. Message-list construction at LLM call time** — replace current accumulating `self._messages` with:
- System prompt (cached)
- Initial task UserMessage (cached)
- `<agent_history>` block in the per-step state UserMessage, built from compacted HistoryItems
- Recent N items kept verbatim (last 3-5 steps)
- Older items: LLM-summarized into a single `<compacted_memory>` string

**4. Compaction trigger** — fire LLM summarization when:
- History char count > 40,000 (~10k tokens)
- AND last summarization was ≥6 steps ago (avoid thrash)

**5. Compaction LLM call** — separate cheap LLM call (gemini-3-flash-minimal) given:
- Current `<compacted_memory>` string
- Items 0..N-keep_last from history
Return: new `<compacted_memory>` string (≤6000 chars).

**6. Tool result lifecycle change** — large extract / page_text results no longer go directly into ToolResultMessage. Instead:
- `extracted_content` stored on the HistoryItem with `include_in_memory=False`
- The CURRENT-step state UserMessage gets a `<read_state>` block with the just-completed extracts
- Next step: `<read_state>` cleared
- This is the upstream `include_extracted_content_only_once` pattern done correctly (the v0.11.2 attempt failed because it was bolted on without the HistoryItem foundation)

### Risk profile
- **MEDIUM on accuracy**: structured memory + LLM summary should preserve agent state better than the current native message list does for long tasks
- **HIGH on implementation complexity**: this is a real architectural rewrite
- **Cache-shape risk**: any change to message structure shifts the cached prefix → one-time cache rebuild per session amortized; but per the v0.11.20 lesson, the LLM may notice the structural change and react
- **Compaction LLM cost**: each summarization call is ~$0.001-0.005. Fired at most every 6 steps means ~3-4 calls per 20-step task = ~$0.003-0.020/task overhead. Net savings only if accumulated history savings > overhead.
- **Mitigation 1**: instrumentation. Log per-call: chars saved by compaction, summarization LLM cost, accuracy on tasks that crossed the compaction threshold vs those that didn't.
- **Mitigation 2**: feature flag (env var `BU_RS_HISTORY_COMPACTION=1`). Default OFF. A/B in eval.

### Estimated impact
- Cost: **−15-30% per task** on long tasks (≥15 steps) — the median task IS long enough to benefit
- Tokens: **−40-60% on cached prefix** at steady state
- Accuracy: should be neutral or slight positive (better-structured memory than raw conversation)

This is the **biggest cost lever remaining** if implemented correctly. Per user's intuition: "Option 2 might be biggest cost saver tbh."

### Effort
5-10 days:
- Day 1-2: HistoryItem + ActionRecord dataclasses, refactor `_run_tool` to populate them
- Day 3: replace `_messages` builder to construct from HistoryItems
- Day 4: implement compaction trigger + summarization LLM call
- Day 5: ToolResult lifecycle (move extracted_content to HistoryItem)
- Day 6-8: eval-validate, tune compaction thresholds
- Day 9-10: bug-fixes, edge cases (resume from injected state, error propagation)
